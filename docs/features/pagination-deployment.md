## 🔍 关键改进体现

### 改进1：不再依赖页码显示

**旧方法问题：**
```
第1页显示"1 2" → 提取到total_pages=2
第2页显示"1 2 3" → 提取到total_pages=3（被绕过了）
实际：脚本仍会按原始total_pages=2采集
```

**新方法：**
```
获取第1页 → 查找page=2链接 → 找到! 继续
获取第2页 → 查找page=3链接 → 找到! 继续
获取第3页 → 查找page=4链接 → 找不到! 停止
实际：正确采集了3页
```

### 改进2：自动停止无效采集

**旧方法问题：**
```
maxPages=10, 实际3页
脚本仍会尝试采集4-10页（浪费请求）
```

**新方法：**
```
maxPages=10, 实际3页
采集3页后检查无page=4 → 立即停止
结果：节省请求，更高效
```

### 改进3：清晰的反馈

**旧方法：**
```
无法判断是真的没有页面，还是提取失败
```

**新方法：**
```
✓ 版块第 3 页没有下一页链接，采集完毕
清晰显示停止的原因
```

## 🔧 故障排查

### 问题1：日志没有显示"有下一页"信息

**检查项：**
- [ ] 后端容器是否重启？ → 重启: `docker compose restart backend`
- [ ] 爬虫是否在访问论坛？ → 检查网络连接
- [ ] 论坛HTML结构是否变化？ → 检查页面源码

### 问题2：仍然采集了超过实际页数的空页面

**排查步骤：**
```python
# 手动测试 has_next_page() 函数
html = fetch_page(section_url)
for page in range(1, 5):
    result = has_next_page(html, page)
    print(f"Page {page} has next: {result}")
    if result:
        html = fetch_page(build_url(section_url, page + 1))
```

### 问题3：采集中途停止

**可能原因：**
- 网络中断 → 检查日志中的"无法获取"消息
- 论坛限流 → 增加延迟或检查IP是否被封
- 页面格式变化 → 检查提取链接的逻辑
