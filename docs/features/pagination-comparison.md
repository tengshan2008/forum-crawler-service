# 分页采集改进 - 对比分析

## 问题回顾

论坛网站的分页显示BUG导致系统采集时的页码判断错误：

### 实际现象
```
第1页：显示 "1 2"（有2页）
↓ 用户翻页
第2页：显示 "1 2 3"（有3页！）
↓ 用户再翻页
第3页：显示 "1 2 3 4"（又有4页！）
```

### 问题根源
- 论坛的分页按钮显示不稳定
- 每一页显示的"最大页码"都不同
- 系统依赖这个显示来判断是否有更多页

---

## 解决方案对比

### 原始方案（依赖页码提取）

```python
# 第1步：获取首页
html = fetch_page(section_url)

# 第2步：一次性提取"总页数"
total_pages = extract_page_numbers(html)  # 可能返回2, 3, 4...

# 第3步：循环采集所有页面
for page_num in range(2, total_pages + 1):
    page_url = build_url(section_url, page_num)
    page_html = fetch_page(page_url)
    extract_links(page_html)
```

**问题：** 依赖 `extract_page_numbers()` 的结果，但这个值不准确

### 改进方案（逐页检查）

```python
# 第1步：获取首页
html = fetch_page(section_url)
extract_links(html)
current_page = 1

# 第2步：逐页采集，检查是否有下一页
while current_page < max_pages:
    # 检查当前页是否有下一页链接
    if not has_next_page(html, current_page):
        break  # 没有下一页链接，停止
    
    # 获取下一页
    next_page_url = build_url(section_url, current_page + 1)
    html = fetch_page(next_page_url)
    if not html:
        break  # 无法获取，停止
    
    extract_links(html)
    current_page += 1
```

**优势：** 不依赖页码显示，实际测试链接

## 核心改进：has_next_page() 方法

### 工作原理

```python
def has_next_page(self, html, current_page):
    """检查当前页是否有下一页链接"""
    next_page = current_page + 1
    
    # 查找HTML中指向下一页的链接
    all_links = find_all('a')
    for link in all_links:
        href = link.get('href')
        if 'page=' + next_page in href:
            return True  # 找到下一页链接
    
    return False  # 没有找到下一页链接
```

### 检查流程

```
当前HTML中的链接:
  <a href="...page=1">1</a>  ✓ 有第1页
  <a href="...page=2">2</a>  ✓ 有第2页
  <a href="...page=3">3</a>  ✓ 有第3页
  <!-- 没有 page=4 的链接 -->

has_next_page(html, current_page=3) ?
  查找 page=4 的链接
  → 找不到
  → 返回 False
  → 停止采集
```

## 代码对比

### 提取页码方式（原始）

```python
# 原始方法：一次性提取所有页码
def extract_page_numbers(self, html):
    page_numbers = set()
    for link in soup.find_all('a'):
        if 'page=' in link['href']:
            page_numbers.add(extract_number(link['href']))
    return max(page_numbers) if page_numbers else 1
```

**缺陷：**
- ❌ 只看链接，不确认能否访问
- ❌ 数字最大的不一定真的存在
- ❌ 论坛BUG时返回错误值

### 检查下一页方式（改进）

```python
# 改进方法：逐个检查下一页
def has_next_page(self, html, current_page):
    next_page = current_page + 1
    for link in soup.find_all('a'):
        if f'page={next_page}' in link['href']:
            return True  # 确认找到
    return False  # 确认没有
```

**优势：**
- ✅ 精确检查具体页码
- ✅ 只确认存在的页面
- ✅ 不受论坛BUG影响

## 容错能力对比

| 场景 | 原始方案 | 改进方案 |
|------|---------|---------|
| 网络间歇性中断 | ❌ 继续采集空页面 | ✅ 检测到立即停止 |
| 页面格式变化 | ❌ 提取页码失败 | ✅ 继续逐页检查 |
| 论坛隐藏某些页 | ❌ 可能漏采或错采 | ✅ 跟随实际链接 |
| 版块突然缩减 | ❌ 空白采集 | ✅ 自动检测停止 |
| 采集速度限制 | ❌ 可能触发限流 | ✅ 逐页延迟更稳定 |

## 性能影响

### 网络请求数

```
原始：1 (获取首页) + N (采集N页)
改进：1 (获取首页) + 实际页数 (逐页采集)
```

**结果：** 无区别（都是顺序采集）

### 响应时间

```
原始：即时获得"总页数" + 采集所有页
改进：采集第1页后动态获知是否有第2页 + 采集所有页
```

**结果：** 改进方案更稳妥（不会浪费请求采集空页）

### 内存占用

```
原始：保存所有已提取的页码 + 采集结果
改进：只保存当前页信息 + 采集结果
```

**结果：** 改进方案内存占用略少

## 用户配置的影响

### maxPages 参数

**原始方案：**
```
maxPages=5 → 采集第 1-5 页（即使第3页后无页面）
```

**改进方案：**
```
maxPages=5 → 最多采集5页，但如果第3页后无页面则采集3页
```

**优势：** maxPages变成真正的"最多"而不是"必须"
